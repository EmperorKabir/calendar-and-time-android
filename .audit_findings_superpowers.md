## PHASE 2 — Pattern analysis: the recurring failure mode

Comparing the working parts against the broken parts produces one dominant pattern, and it explains
most of the findings below:

> **A defect is repaired by suppressing the symptom's *output* rather than by conditioning it on the
> state that made it wrong.**

Three independent instances:
1. **V7** — guidance shown in the wrong mode was fixed by making the branch unreachable (F-03), not by
   testing `willUseCalendar` — which was written for exactly this purpose and now has zero callers.
2. **Chained icon mode** — proven not to work, so `chainedEngineEnabled` was hardcoded `false`
   (`Settings.kt:108`) rather than removing the 109-line engine, its channel, its key and its setter.
   The dead branch now costs six `NotificationManager` IPCs on every settings emission (F-14).
3. **`setNotificationEngine` / `setOverlayEngine` / `setChainedEngine`** — superseded by the
   `DisplayMode` derivation, so the *read* side was deleted while the *write* side was left in place

The same pattern predicts where the next bug will be: any place where a value is computed but its
consumer was removed. That is precisely `IconDisplay.willUseCalendar` (F-04).

## PHASE 3 — Findings, with hypothesis, failure scenario, fix and preservation gate

### F-01 — `OverlayEngine.stop()` orphans the window when `removeView` throws
**Severity: HIGH** · `app/src/main/java/…/engine/overlay/OverlayEngine.kt:68–71`

```kotlin
override fun stop() {
    view?.let { runCatching { windowManager.removeView(it) } }
    view = null
}
```

**Evidence checked.** `view = null` executes unconditionally, outside the `runCatching`. There is no
inspection of the `Result`. `windowManager.removeView` throws `IllegalArgumentException("View … not
attached to window manager")` when the view was already detached, and OEM window managers throw
`BadTokenException` from this path when the overlay token has been revoked.

**Hypothesis.** If `removeView` throws for any reason other than "already detached", the window
remains attached to the WindowManager while the only reference to it is discarded. `start()` then sees
`view == null` and adds a **second** window (`:34`, `:63`).

**Failure scenario.** ColorOS revokes `SYSTEM_ALERT_WINDOW` while the overlay is showing (it does this
on some background-restriction transitions) → the user switches COMPACT → `stop()` → `removeView`
throws → reference dropped, window still on screen showing a frozen time → user switches back to
FULL_TEXT → `start()` adds window #2. **This is V1 and V2 exactly, reachable again despite the
singleton fix.** The log's own V2 wording — "orphaned windows are never updated again and never
removed" — describes this code path.

**Fix.**
```kotlin
override fun stop() {
    val current = view ?: return
    val removed = runCatching { windowManager.removeView(current) }
    if (removed.isSuccess) view = null
    else runCatching { windowManager.removeViewImmediate(current) }
        .onSuccess { view = null }
    // if both fail, KEEP the reference so a later stop() can retry
}
```

**PRESERVATION GATE.**
- *Why safe:* the change only narrows when `view` is set to `null`; it never adds a window and never
  skips a removal that succeeds today.
- *What prior bug the code may be defending:* the `runCatching` was added to stop a crash when
  `removeView` is called on an already-detached view — a real `IllegalArgumentException` that would
  otherwise kill the service during mode changes. That crash is the reason the catch exists.
- *Why that cannot occur:* the proposed code still catches the same exception. It only differs in what
  it does afterwards. The already-detached case reaches `removeViewImmediate`, which also throws and
  is also caught; the reference is retained, and the *next* `stop()` retries — a no-op cost, not a
  crash. The only behavioural difference is that a genuinely-stuck window stays eligible for removal
  instead of being leaked.

### F-02 — `OverlayEngine.start()` swallows `addView` failure; the user is told the mode is active
**Severity: HIGH** · `OverlayEngine.kt:62–66`, `MainActivity.kt:258–277`

**Evidence checked.**
```kotlin
runCatching {
    windowManager.addView(textView, layoutParams())
    view = textView            // only reached on success — correct
}
```
The success/failure `Result` is discarded. `DisplayController.applySettings:121` calls `start()` and
never asks whether a window exists. `MainActivity` gates the radio buttons only on
`Settings.canDrawOverlays(context)` (`:240`, `:266`, `:276`).

**Hypothesis.** `canDrawOverlays()` returning `true` is not sufficient for `addView` to succeed.
`addView` throws `WindowManager.BadTokenException` when the app-overlay token is refused (OEM
restriction, work-profile policy, or the permission revoked between the check and the call), and
`SecurityException` on some MIUI builds even with the permission granted.

**Failure scenario.** User grants "draw over other apps", selects **Full text**. The radio button
selects, the mode persists, `PreviewCard` shows the overlay text, and the notification icon is turned
**off** (`Settings.kt:106`, FULL_TEXT ⇒ `notificationEngineEnabled = false`). `addView` throws. The
result: **nothing at all in the status bar, no error, and the icon that would have been the fallback
is deliberately disabled.** This is the exact symptom of V3 ("Compact mode shows nothing in the status
bar" — measured 2.9 s–5.1 s and 18.0 s–18.5 s blank runs) arriving by a second route, and it is
permanent rather than transient.

**Fix.** Return the outcome and act on it:
```kotlin
fun start(): Boolean = if (view != null) true else if (!canDraw()) false else
    runCatching { windowManager.addView(textView, layoutParams()); view = textView }
        .isSuccess
```
In `DisplayController.applySettings`, when `overlayEngineEnabled && !overlayEngine.start()`, force
`notificationEngine.setIconVisible(true)` so the compact icon remains as a working fallback, and
expose an `overlayFailed` flag the settings screen can surface ("Full text could not be drawn on this
device — showing the compact icon instead").

**PRESERVATION GATE.**
- *Why safe:* purely additive — the existing `runCatching` and the `view != null` guard are untouched;
  only a boolean is returned and a fallback added.
- *What prior bug the code may be defending:* the comment at `:32–34` records a real prior bug — a
  second window being stacked. The `runCatching` itself defends against `addView` crashing the
  foreground service, which would take the whole display down.
- *Why that cannot occur:* the guard and the catch both remain. The fallback path only *enables* an
  icon that is already fully implemented and already the default in COMPACT, so it introduces no new
  window and no new notification ID.

### F-03 — The V7 fix is a duplicated `when` condition: the icon guidance is unreachable dead code
**Severity: HIGH (falsifies a documented fix)** · `MainActivity.kt:718–726`

**Evidence checked** — verbatim:
```kotlin
val iconWarning = if (!iconOn) null else when {
    iconDisplay.stackTop != null -> null                       // 719
    iconDisplay.stackTop != null ->                            // 720  ← identical condition
        "There is only room for a few characters here, so the day of the week " +
            "is shown above a large date number. Pick the draw over option if " +
            "you want the whole thing written out."
    iconDisplay.line.isEmpty() -> "Nothing selected to show."  // 724
    else -> null
}
```

**Root cause.** Lines 719 and 720 test the **same** expression. Kotlin `when` evaluates in order, so
line 720's branch is unreachable for every possible input. The message quoted in
`VIDEO_ISSUE_LOG.md` V7 ("Too long for one row, so it is split over two rows…") can never be shown in
any mode.

Line 724 is also unreachable in the case it was written for: when `line.isEmpty()`, `forSpec` renders
with `stackMode` only if `spec.stackMode || line.length > 7` — an empty line is neither, so
`stackTop` is `null` and line 724 *is* reachable. Correction: **724 is reachable; only 720–723 is
dead.** I verified this by tracing `IconDisplay.forSpec` (`IconDisplay.kt:16–25`) rather than assuming.

**Failure scenario.** A user selects the **Full UK** preset (11+ characters). `forSpec` silently
replaces the entire format with a desk calendar (`THU` over `1`) — see F-11. The preview draws that
calendar bitmap, and the one sentence that would explain why their format vanished is unreachable.
The user concludes the app ignored their configuration.

**Why this is the "fixed" claim failing.** V7's complaint was that the guidance showed when Compact was
*not* selected. The correct fix is the `if (!iconOn) null` guard at line 718 — which is present and
correct. The duplicated condition at 719/720 is a second, unintended change that silenced the message
in *all* modes. The fix over-corrected from "always shown" to "never shown".

**Fix.** Line 719's condition should be the *negative* case, and the intended predicate already exists
(see F-04):
```kotlin
val iconWarning = if (!iconOn) null else when {
    iconDisplay.line.isEmpty() && iconDisplay.stackTop == null -> "Nothing selected to show."
    IconDisplay.willUseCalendar(settings.formatSpec, now, Locale.getDefault()) ->
        "Too long for one row, so the weekday is shown above the day number. " +
        "Choose Full text to see the whole format."
    else -> null
}
```

**PRESERVATION GATE.**
- *Why safe:* the `if (!iconOn)` guard — the actual V7 fix — is preserved verbatim, so the regression
  V7 describes (advice shown for an inactive mode) still cannot recur.
- *What prior bug the code may be defending:* V7 itself, plus `MISSED_TASKS` #26 ("Shipped a preview
  that showed the configuration rather than what each engine actually renders").
- *Why that cannot occur:* the message remains inside the `iconOn` branch, so it is impossible to
  render it while Compact is deselected. It becomes conditional on a predicate derived from the same
  `IconDisplay` rule the renderer uses, which strengthens #26's fix rather than weakening it.

### F-04 — `IconDisplay.willUseCalendar` has zero callers and duplicates the threshold rule
**Severity: MEDIUM** · `IconDisplay.kt:27–32`

**Evidence checked.** `grep -n "willUseCalendar" **/*.kt` → one hit, the declaration. No call sites.

**Root cause.** The function was written to power the message that F-03 made unreachable. It now
carries a **second, independent copy** of the `> MAX_SINGLE_LINE` rule (`:32`), separate from the copy
in `forSpec` (`:21`).

**Failure scenario.** A maintainer tunes `MAX_SINGLE_LINE` or changes the seconds-stripping in
`forSpec` and does not update `willUseCalendar` (or vice versa) → the preview's promise and the
renderer's behaviour diverge. The KDoc on the object (`:6–11`) explicitly states the whole purpose of
this file is that the renderer and the preview "can never disagree" — the duplication defeats it.

**Fix.** Express one in terms of the other, eliminating the second copy:
```kotlin
fun willUseCalendar(spec: FormatSpec, now: ZonedDateTime, locale: Locale): Boolean =
    forSpec(spec, now, locale).stackTop != null
```
and wire it up at `MainActivity.kt:718` per F-03.

**PRESERVATION GATE.**
- *Why safe:* `forSpec` is the authority the renderer already uses (`DisplayController.kt:95`, `:138`;
  `MainActivity.kt:687`); deriving the predicate from it cannot make the two disagree by construction.
- *What prior bug the code may be defending:* `MISSED_TASKS` #26 — a preview that did not match the
  engine. This file is the fix for that bug.
- *Why that cannot occur:* the change strictly increases the coupling between preview and renderer,
  which is the direction #26 requires. Behaviour is identical for every input today (both expressions
  reduce to `spec.stackMode || strippedLine.length > 7`).

### F-06 — The Horizontal slider's first 22 % of travel is dead, and its label is wrong
**Severity: MEDIUM** · `MainActivity.kt:835–838` vs `OverlayEngine.kt:128–136`

**Evidence checked.** Slider range `0f..(screenWidth - 120f)` (`MainActivity.kt:836`); engine clamp
lower bound `maxOf(clockReserve(), cutoutRight())` where `clockReserve() = width * 0.22f`
(`OverlayEngine.kt:129`, `:134`). `SliderRow` prints `"$label: ${value.toInt()}"`
(`MainActivity.kt:865`) — the *stored* value, never the *effective* one.

**Failure scenario.** On a 1440 px display, every slider position from 0 to 316 produces the identical
on-screen result. The user drags through a quarter of the control seeing no movement, reads
"Horizontal: 150", and the text is at 316. `MISSED_TASKS` B13 says these sliders were "never
exercised" — this is what exercising them would have found.

**Fix.** Make the UI range the engine's real range and show the effective value. Expose the clamp:
```kotlin
// OverlayEngine
fun minimumX(): Int = maxOf(clockReserve(), cutoutRight())
fun maximumX(): Int = (screenWidth() - 120).coerceAtLeast(minimumX())
// MainActivity
SliderRow("Horizontal", style.offsetX.coerceIn(min, max).toFloat(), min.toFloat()..max.toFloat())
```

**PRESERVATION GATE.**
- *Why safe:* the clamp itself is unchanged; only the control's range is aligned to it. No offset that
  is rejected today becomes accepted.

### F-07 — Overlay geometry is computed from the *application* `Resources`, not the display
**Severity: HIGH (breaks `PROJECT_RULES` rule 1: foldables, multi-window)** ·
`OverlayEngine.kt:129`, `:133`, `:140`

**Evidence checked.** All three call `context.resources.displayMetrics.widthPixels`, where `context`

**Hypothesis.** The application `Configuration` tracks the process's top activity's bounds. In

and call `refreshPlacement()` from `onConfigurationChanged` in **both** hosts (see F-10).

**PRESERVATION GATE.**

### F-08 — Saved-preset encoding silently destroys presets, including neighbouring ones
**Severity: MEDIUM (silent data loss)** · `Settings.kt:157–212`

**Evidence checked (byte-level).** `cat -A` confirms the record separator is **U+001E** and the field
separator is **U+001F**. Encoding is `joinToString(RS)` over presets and `joinToString(US)` over 16
fields (`:158`, `:177`). Decoding is `raw.split(RS)` → `entry.split(US)` → `if (f.size != 16) return@mapNotNull null` (`:182–184`).

Kotlin's `String.split(String)` — unlike Java's regex `split` — does **not** drop trailing empty
strings, so a well-formed record always yields exactly 16 fields. The size check is therefore an exact
integrity test, and *any* deviation results in a silent `null`.

**Hypothesis and reasoning about the delimiter characters.** The name field is `f[0]`, written first
and unescaped. Two injection cases:

*Case A — name contains U+001F (US).* Encoding produces 17 US-separated fields for that record.
Decoding yields `f.size == 17` → `null` → **the preset the user just saved silently does not appear
in "Your saved presets"**. The Save button clears the text field (`MainActivity.kt:341`), so the UI
signals success.

*Case B — name contains U+001E (RS) — strictly worse.* Encoding splits that record into two at decode
time. If the corrupted preset is not the last, the first fragment concatenates the **preceding
preset's complete 16 fields** with the partial name, producing ≥17 fields → dropped. **One bad
character in one name silently deletes a different, previously-working preset.** If it *is* the last
preset, the second fragment can contain exactly 16 fields and decodes as a valid preset with a
**truncated name**, which then cannot be deleted by `deletePreset` (which matches on the full name).

**Reachability — reasoned honestly.** `OutlinedTextField` with `singleLine = true`
(`MainActivity.kt:329–335`) applies no character filter. A stock Android soft keyboard cannot emit
U+001E/U+001F. Reachable via: (a) clipboard paste of arbitrary text — trivial, e.g. copying from a
terminal emulator, a text file, or a web page containing control characters; (b) a physical/Bluetooth
keyboard, where `Ctrl+^` and `Ctrl+_` produce exactly these code points; (c) a third-party or IME
keyboard with a symbol palette. **Probability: low. Consequence: silent, unrecoverable loss of an
unrelated saved preset. Detectability by the user: zero.**

**A second, unconditional defect in the same code.** `savePreset` de-duplicates with
`equals(name, ignoreCase = true)` (`:148`) while `deletePreset` matches with `==` (`:153`). Saving
"Work" then "work" removes "Work"; the two methods disagree about identity. Not currently
user-visible because `MainActivity.kt:356` always passes the exact stored name, but it is a latent
trap for any future rename/import feature.

**Fix.** Sanitise on the way in and validate on the way out:
```kotlin
private fun sanitise(name: String) = name.filterNot { it == RECORD_SEP || it == FIELD_SEP }.take(64)
suspend fun savePreset(name: String, spec: FormatSpec) {
    val clean = sanitise(name).trim()
    if (clean.isEmpty()) return
    …filterNot { it.name.equals(clean, ignoreCase = true) } …
}
suspend fun deletePreset(name: String) = … filterNot { it.name.equals(name, ignoreCase = true) }
```
and surface the rejection in `MainActivity` rather than clearing the field on a no-op save.

**PRESERVATION GATE.**
- *Why safe:* sanitising only removes two non-printing control characters that can never be part of a
  meaningful preset name and that the format reserves. Every name a user can produce with a normal
  keyboard round-trips byte-identically today and after the change.
- *What prior bug the code may be defending:* the `runCatching` + `f.size != 16` guard
  (`:184`, `:185`, `:210`) defends against a genuine crash — a partially-written or older-format
  DataStore value throwing `IllegalArgumentException` from `enumValueOf` and killing the settings
  flow, which would take the whole app down (see F-16).
- *Why that cannot occur:* both guards remain untouched. The change adds an *input* filter; it does
  not relax the *output* validation, so malformed legacy data is still discarded rather than throwing.

**Evidence checked — ordering.**

   ```kotlin
       insets
   ```

3. Add `onConfigurationChanged` to `KeepAliveAccessibilityService` calling
   `controller?.overlayEngine?.refreshPlacement()`, mirroring `DisplayService.kt:48–52`.

**PRESERVATION GATE.**
- *Why safe for (1):* `view` is reset to `null` on failure, preserving the exact invariant the
  `view != null` guard at `:34` depends on — the guard's contract ("a non-null view means a window is
  attached") is restored on the error path, so no window can be double-added.
- *What prior bug (1) may be defending:* V1/V2 — a second overlay window. The current ordering was

- *Why that cannot occur:* the failure branch explicitly restores `null`, so the post-condition is
  identical to today's for both outcomes. The only difference is that during `addView` itself the

- *Why safe for (2):* `refreshPlacement()` already guards on `view ?: return` and wraps

- *Why safe for (3):* it duplicates an existing, shipped call on the other host.

### F-12 — Vertical centring uses a deprecated, non-linear-scaling-unsafe conversion
**Severity: MEDIUM** · `OverlayEngine.kt:155–157`

**Evidence checked.**
```kotlin
val textHeight = (style.textSizeSp * context.resources.displayMetrics.scaledDensity).toInt()
y = ((barHeight - textHeight) / 2).coerceAtLeast(0) + style.offsetY
```
Two independent errors:
1. `DisplayMetrics.scaledDensity` is deprecated as of API 34. Since Android 14, font scaling is
   **non-linear**, so a single multiplier is no longer a correct sp→px conversion; the documented
   replacement is `TypedValue.applyDimension(COMPLEX_UNIT_SP, sp, metrics)`.
2. Even with a correct conversion, the **font size is not the text height**. Glyph height is
   `descent − ascent`, typically ≈1.15–1.25× the point size. `textHeight` is therefore systematically
   under-estimated, so `(barHeight − textHeight)/2` is too large and the text sits a few pixels low.

**Failure scenario.** A user with system font scale at 1.3 or above (very common accessibility
setting) gets progressively worse vertical alignment on Android 14+. `MISSED_TASKS` #31 records that
"Overlay text sat too high" was fixed by this centring — the fix exists and improved matters, but the
residual error is in the opposite direction and grows with font scale.

**Fix.**
```kotlin
val px = TypedValue.applyDimension(
    TypedValue.COMPLEX_UNIT_SP, style.textSizeSp, context.resources.displayMetrics)
val paint = (view as? TextView)?.paint
val textHeight = paint?.let { (it.descent() - it.ascent()).toInt() } ?: (px * 1.2f).toInt()
```

**PRESERVATION GATE.**
- *Why safe:* on API < 34 with font scale 1.0, `applyDimension` and `scaledDensity` produce identical
  values, so the common case is bit-for-bit unchanged.
- *What prior bug the code may be defending:* `MISSED_TASKS` #31 — text sitting too high. The centring
  expression, including `coerceAtLeast(0)` and the `+ style.offsetY` nudge, is that fix.
- *Why that cannot occur:* the expression's shape is preserved exactly; only the `textHeight` term
  becomes more accurate, which moves the text *up* toward true centre. The `coerceAtLeast(0)` floor
  still prevents a negative `y`, and the user's manual nudge still applies on top.

### F-16 — `runCatching { readSettings(p) }.getOrElse { defaults() }` can silently wipe the entire configuration
**Severity: HIGH (latent)** · `Settings.kt:85–87`

**Evidence checked.**
```kotlin
val flow: Flow<AppSettings> = context.dataStore.data.map { p ->
    runCatching { readSettings(p) }.getOrElse { defaults() }
}
```
`defaults()` (`:89–100`) sets `displayEnabled = false`.

**Analysis — is it reachable today?** I traced every expression inside `readSettings` (`:102–144`):
every key read goes through `p.safe()` which catches (`:218–220`); every enum parse goes through
`enumPref` which catches (`:214–215`); `decodePresets` catches per record (`:185`, `:210`);
`toLongOrNull(16)` cannot throw. **I therefore assess the catch as currently unreachable** — and I
state that as an assessment from reading, not a proven fact.

That does not make it harmless; it makes it a trap. Any future field added to `readSettings` without
its own guard — the natural way to add a field — inherits a catch that converts *any* exception into
"the user has no settings".

**Failure scenario (the moment it becomes reachable).** A maintainer adds
`overlayCornerRadius = p.safe(Keys.radius)!!.toFloat()` and ships it. On a device where the key is
absent, the NPE is caught here. The user's display **turns itself off** (`displayEnabled = false`),
their format resets to `compactDate`, their saved presets vanish from the list, and their overlay
calibration reverts — on every emission, permanently, with nothing in logcat.

```kotlin

    .onFailure { Log.e(TAG, "Settings decode failed; falling back to defaults", it) }
    .getOrElse { defaults().copy(displayEnabled = true) }   // never silently switch the product off
```
Better still, return a `Result<AppSettings>` or add a `degraded: Boolean` field the UI can surface.

**PRESERVATION GATE.**
- *Why safe:* the catch is preserved, so the crash-prevention property is unchanged. Only the
  observability and the `displayEnabled` value change.
- *What prior bug the code may be defending:* an uncaught throw inside a `Flow.map` cancels the
  collector. In `DisplayController` that would permanently stop settings from being applied

### F-22 — `DisplayController` singleton captures the first caller's `CoroutineScope` and can be permanently deafened
**Severity: CRITICAL** · `DisplayController.kt:23–42`, `:55–60`; `MainActivity.kt:163–168`;
`DisplayService.kt:35`, `:40`, `:54–58`

This is the mandate's item 7. I traced both directions.

**Evidence checked.**
- `DisplayController.kt:24–26` — `scope` is a constructor `val`, fixed at first construction.
- `:37–41` — `get()` returns the cached `instance` for every subsequent caller; the `scope` argument
  of later callers is **silently discarded**.
- `:57–59` — `start()` does `repository.flow.onEach { applySettings(it) }.launchIn(scope)`.
- `MainActivity.kt:163` — `val fallbackScope = rememberCoroutineScope()`. This scope is **cancelled
  when the composition leaves**.
- `MainActivity.kt:164–168` — `remember { DisplayController.get(context.applicationContext, fallbackScope) }`.
- `DisplayService.kt:35` — the service has its own scope; `:56` cancels it in `onDestroy`.
- `instance` is **never** set back to `null`, not even by `stop()` (`:62–68`).

**One thing the code gets right, which I verified rather than assumed:** `get()` calls
`context.applicationContext` at `:39`, and `MainActivity` also passes `applicationContext`. **There is
no Activity `Context` leak.** I also checked thread-safety: `settings` (`:52`) is a non-volatile `var`
written by `applySettings`/`renderOnceFrom` and read by `renderNow` — but every writer and reader runs
on the main thread (`Dispatchers.Main.immediate` for both services; `AndroidUiDispatcher.Main` for the
composition; `TickSource`'s `Handler(Looper.getMainLooper())` at `TickSource.kt:24`). **No data race.**
`BootReceiver` uses `Dispatchers.Default` (`BootReceiver.kt:18`) but never touches the controller.

**Failure scenario A — Activity destroyed while the Service holds the controller (CRITICAL).**
1. Fresh process. User launches the app. `SettingsScreen` composes → `get()` **constructs** the
   singleton bound to the composition scope `S₁`.
2. User enables the display → `DisplayService.start()` → `onCreate` → `get()` returns the **same**
   instance (still bound to `S₁`) → `controller.start()` launches the settings collector **into the
   Activity's composition scope**.
3. User presses Back. The composition leaves; `S₁` is cancelled.
4. The service is alive; its controller's settings collector is **dead**.
5. `launchIn` on a cancelled scope returns an already-cancelled `Job` — **no exception, no log, no
   crash**. The failure is completely silent.

**What actually breaks.** Three things happen only in `applySettings` and never in `renderOnceFrom`
(`:74–90`):
- `tickSource.setSecondsWanted(...)` (`:128–130`) → **enabling seconds never starts the ticker**; the
  overlay's live seconds silently stop working.
- `slotEngine.start()/stop()` (`:120`) → the "Extra icon slots" toggle becomes inert.
- `chainedEngine.start()/stop()` (`:119`).
Additionally `onStopRequested?.invoke()` (`:109`) never fires, so a settings-driven shutdown cannot
stop the service.

**Failure scenario B — Service destroyed while the Activity lives (the "vice versa" case).**
`DisplayService.onDestroy` (`:54–58`) calls `controller.stop()` on the **shared** singleton →
`tickSource.stop()` + every engine stopped — **even though the Activity is in the foreground and had
the display running via `renderOnceFrom`**. The Activity's `fallbackController` still points at the
now-stopped controller. `renderOnceFrom` restarts the notification and overlay engines but **never
calls `tickSource.start()`**. Result: **the clock freezes at the last rendered minute while the app is
open**, and only a successful service restart recovers it. If the FGS start is refused (F-23), it
never recovers.

**Failure scenario C — collector accumulation.** `START_STICKY` (`DisplayService.kt:46`) means the
system recreates the service after a kill → `onCreate` → `get()` (same instance) → `controller.start()`
again. `TickSource.start()` is guarded (`TickSource.kt:58`, `if (registered) return`) — good — but
`launchIn` is **not**. Under scenario A's ordering the scope is `S₁`, which the service never cancels,
so **each restart adds another live collector**, each running `applySettings` on every emission:
N× engine start/stop churn, N× `renderNow`, N× the IPC costs in F-14/F-18/F-21.

**Failure scenario D — full flavour, two hosts, one callback slot.** `onStopRequested` is a single
nullable field (`:53`). `DisplayService.kt:41` sets `{ stopSelf() }`; `KeepAliveAccessibilityService.kt:24`
sets `{ controller?.stop() }`. Last writer wins. If the accessibility service connects **after** the
foreground service, disabling the display invokes `controller.stop()` instead of `stopSelf()` — **the
foreground service and its notification persist indefinitely**, defeating the full flavour's stated
purpose ("no notification at all", `README` Flavours section).

**Fix.** Four changes, smallest first.
1. **Do not capture a caller's scope.** Give the controller its own:
   ```kotlin
   class DisplayController private constructor(private val context: Context) {
       private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)
       fun get(context: Context) = …   // drop the scope parameter entirely
   }
   ```
2. **Make `start()` idempotent**, mirroring `TickSource`'s own guard:
   ```kotlin
   private var settingsJob: Job? = null
   fun start() {
       tickSource.start()
       if (settingsJob?.isActive == true) return
       settingsJob = repository.flow.onEach { applySettings(it) }.launchIn(scope)
   }
   ```
3. **Reference-count the hosts** so one host's destruction cannot tear down another's display:
   ```kotlin
   private val hosts = java.util.concurrent.atomic.AtomicInteger(0)
   fun attach() { hosts.incrementAndGet(); start() }
   fun detach() { if (hosts.decrementAndGet() <= 0) stop() }
   ```
   `DisplayService.onCreate`/`onDestroy` and `KeepAliveAccessibilityService` call `attach`/`detach`;
   `MainActivity` keeps using `renderOnceFrom` only.
4. **Make `onStopRequested` a list**, so both hosts are notified:
   `private val stopListeners = mutableListOf<() -> Unit>()` with `addStopListener`/`removeStopListener`.

**PRESERVATION GATE.**
- *Why safe for (1):* the controller already stores only `applicationContext`, so an owned scope has
  the same lifetime as the object and cannot leak an Activity. Every current caller passes a
  main-dispatcher scope, so the dispatcher is unchanged and the main-thread confinement that makes
  `settings` race-free (verified above) is preserved exactly.
- *What prior bug (1)–(3) may be defending:* **V1 and V2.** The singleton exists specifically so that
  "exactly one overlay window and one notification can ever exist" (KDoc, `:32–36`). Nothing proposed
  here relaxes that: `get()` still returns one instance, `OverlayEngine` is still constructed once at
  `:45`, and the `view != null` guard at `OverlayEngine.kt:34` is untouched.
- *Why V1/V2 cannot recur under (3):* reference counting changes only *when* `stop()` is called, never
  *how many engines exist*. With hosts ≥ 1 the engines stay up; at 0 they are torn down exactly as
  today. The count can only make teardown **later**, and a late teardown cannot create a second
  window — only an extra `start()` could, and that is guarded.
- *What prior bug (4) may be defending:* `MISSED_TASKS` #25 — "the foreground service icon ignoring its
  own toggle went unnoticed". `onStopRequested` is how a settings-driven disable reaches the host.
- *Why that cannot occur under (4):* a list strictly increases the set of hosts notified. The
  play flavour has exactly one host, so its behaviour is identical; the full flavour gains the
  notification it is currently losing.

`android:supportsRtl="true"` (`AndroidManifest.xml:27`) — a claim of RTL support the app cannot honour

Related: the overlay uses `Gravity.TOP or Gravity.START` (`OverlayEngine.kt:152`) while
`clockReserve()` (`:128–129`) unconditionally reserves the **leading 22 %** on the assumption that the
OEM clock is at the left. In an RTL configuration `START` resolves to the right edge while the reserve
maths still assumes left-to-right, so the clamp protects the wrong side.

**Fix.** Extract to `strings.xml` with `%s`/`%d` placeholders; resolve `clockReserve` against the
resolved layout direction (`context.resources.configuration.layoutDirection`).

**PRESERVATION GATE.** *Why safe:* string extraction is mechanical and the default `values/strings.xml`
preserves the exact current English text, so no shipped wording changes. *Prior bug defended:* the
V7 fix depends on *which* strings appear under *which* condition — the conditions live in Kotlin and
are untouched by extraction. *Why that cannot occur:* only the literals move; every `if`/`when` gating
them stays in place, so no string can begin appearing in a mode it does not appear in today.

### F-28 — `allowBackup="true"` restores pixel-valued overlay offsets onto a different screen
**Severity: MEDIUM** · `app/src/main/AndroidManifest.xml:23`; `Settings.kt:77–78`, `:98`

**Evidence checked.** `android:allowBackup="true"` with **no** `android:dataExtractionRules` and no
`android:fullBackupContent`. `overlayX`/`overlayY` are `intPreferencesKey` storing **raw device
pixels** (`OverlayEngine.kt:135` consumes `style.offsetX` directly as a pixel `x`).

**Failure scenario.** A user backs up from a 1440 px phone with `offsetX = 900`, restores onto a
1080 px phone. `startX()` clamps to `1080 - 120 = 960`, so 900 survives the clamp, and the text is
drawn at x = 900 in a 180 px-wide window — truncated to an ellipsis. The app appears broken on first
launch of a new device, and the cause (a restored setting) is invisible.

**Fix.** Store the offset as a **fraction of screen width** (a `Float` in 0..1), or exclude the
overlay keys from backup via `dataExtractionRules`. The fraction is preferable — it also fixes the
foldable posture change in F-07.

**PRESERVATION GATE.** *Why safe:* a fraction converts to today's pixel value exactly on the device
where it was set; migration can read the old int once and divide by the current width. *Prior bug
defended:* V5/V10 — offsets that push text off-screen. *Why that cannot occur:* the `startX()` clamp
remains the authoritative guard and operates on the resolved pixel value, so no fraction can produce
an unclamped position.

## §6 — `DisplayMode` state machine: full verification (mandate item 6)

**Source** — `Settings.kt:106–110`:
```kotlin

overlayEngineEnabled      = enumPref(p.safe(Keys.displayMode), COMPACT) != COMPACT
chainedEngineEnabled      = false

displayMode               = enumPref(p.safe(Keys.displayMode), COMPACT)
```

**Exhaustive truth table** (all three enum values; there are no others — `Settings.kt:31`):

| `displayMode` | `notificationEngineEnabled` | `overlayEngineEnabled` | Intended | ✔ |
|---|---|---|---|---|
| `COMPACT` | `COMPACT != FULL_TEXT` = **true** | `COMPACT != COMPACT` = **false** | icon only | ✅ |
| `FULL_TEXT` | `FULL_TEXT != FULL_TEXT` = **false** | `FULL_TEXT != COMPACT` = **true** | overlay only | ✅ |
| `BOTH` | `BOTH != FULL_TEXT` = **true** | `BOTH != COMPACT` = **true** | both | ✅ |

**The derivation is correct for every mode.** `defaults()` (`:89–100`) is consistent with it
(`COMPACT`/`true`/`false`). Downstream consumption is also correct:
`DisplayController.kt:117` (`setIconVisible`), `:121` (overlay), `:128–130` (seconds ride the overlay
only), and `MainActivity.kt:696` / `:745` (preview headings) all read the derived flags rather than
re-deriving. **No mode maps to an unintended engine set.** I verified this rather than assumed it.

**Three defects around an otherwise-correct machine:**

1. **The derivation is triplicated.** `enumPref(p.safe(Keys.displayMode), COMPACT)` is evaluated three
   separate times (`:106`, `:107`, `:110`) — three DataStore lookups and three enum parses per
   emission, and three expressions a maintainer must keep in agreement by hand. The invariant
   `notificationEngineEnabled == (displayMode != FULL_TEXT)` is enforced **nowhere**: `AppSettings`
   (`:35–46`) is a plain data class whose three fields can be constructed inconsistently by any caller.
   **Fix:** computed properties on `AppSettings` (F-15's fix). *Preservation gate:* the truth table
   above proves the computed form is value-identical for all three modes; `defaults()` already agrees.

2. **`chainedEngineEnabled = false` hardcode** — see **F-14** for the full analysis, the six-IPC cost,
   and the preservation gate covering `MISSED_TASKS` #24's orphaned-notification defence.

3. **`slotEngineEnabled` default `true`** — see **F-21**. Combined with `renderNow`'s per-tick call it
   costs three `PackageManager` IPCs per tick for a feature no user can install.

**One further inconsistency worth recording:** `AppSettings.displayEnabled` is the master switch, but
`renderOnceFrom` (`DisplayController.kt:76–80`) stops only `notificationEngine` and `overlayEngine`
when it is false, while `applySettings` (`:103–111`) additionally stops `chainedEngine` and
`slotEngine`. The two entry points into the same state machine disagree about what "off" means. With
the Activity as the only live host (F-22 scenario A), turning the display off leaves the slot
companions still showing.
