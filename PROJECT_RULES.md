## Standing rules
1. This is a public-facing Android application for general public use. It must render and function
   correctly across all display sizes, types, densities, resolutions, scale factors, orientations,
   and aspect ratios, and must fully support foldable devices, including fold/unfold posture
   transitions, hinge-aware layouts, and tabletop/flex postures.
2. All code must be clean, idiomatic, and acceptable for Google Play Store publication.
3. Remove as much evidence of AI authorship as possible so the work reads as a skilled human's: no
   AI-attribution in commit messages, trailers, or code comments; no stock "generated by" phrasing;
   no stereotyped scaffolding or boilerplate explanatory comments; human-consistent commit phrasing
   and cadence. The objective is removal of AI-authorship markers ONLY. This does NOT mean
   suppressing functional diagnostic logging, audit trails, or the required evidence trail — kept.
4. All investigations and actions must be evidence-based: every conclusion cites the file, line,
   log entry, documentation, or test result supporting it. No assertion without observable support.
5. Context7 and Superpowers must be used wherever they can apply, erring toward use even in edge
   cases — library and Android/Jetpack API work, mathematical reasoning, investigative analysis,
   planning, and verification. Exempt only genuinely trivial edits touching no API and needing no
   planning or verification.
6. All building and on-device testing phases must invoke the bound build-and-device-test skill
   (below). On-device testing requires a connected, authorised physical device; if none is present,
   that skill stops and flags.
7. All final-stage code audits must invoke the bound efficiency/deep-audit skill (below).
8. Throughout development, the bound diagnostic-logger skill (below) must be used to add on-device
   diagnostics for testing. Diagnostics may remain in release builds during development and are
   stripped only manually, at the very end, on the user's explicit prompt — never automatically.
9. Every change, throughout the entire project lifecycle, is committed and pushed to GitHub
   automatically — not only the initial commit.

## ANTI-DEFERRAL SAFEGUARD (added 2026-07-28 at the user's instruction; binding)
The user has forbidden deferral in any form. These are hard rules, not guidance.

1. **Never end a message with forward-looking work.** No "next actions", "next steps",
   "next session", "immediate priorities", "what remains", "still outstanding",
   "to finish", "picking up from", "priority for later", or any list of unfinished items.
   These phrases are BANNED in user-facing output.
2. **Never cite my own context, budget, token limits, or capacity as a reason to stop,
   summarise, or hand off.** The user has explicitly withdrawn permission to reason about
   this out loud or to let it shape the plan. Work until the work is done.
3. **When an item finishes, immediately start the next outstanding item** from
   `docs/MISSED_TASKS.md`. Do not report and wait. Do not ask which one unless two items
   genuinely conflict.
4. **A report describes only what was done and what was measured.** Blockers are stated as
   a specific blocker plus the exact action that unblocks it, never as a to-do list.
5. **`docs/MISSED_TASKS.md` is the single record.** Update it in place: strike through and
   mark DONE with the date and the evidence. Never restate it back to the user as pending
   work.
6. **Verification is part of "done".** An item is only struck through once it has been
   exercised on a device or emulator and the observed result recorded.
7. **Self-check before sending any message:** does it contain a forward-looking list, a
   mention of my limits, or an unfinished item presented as the user's decision? If yes,
   delete that content and continue working instead.
